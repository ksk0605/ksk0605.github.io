## 떠오른 생각 (원문)

> 거대한 흐름을 워크플로우로 정리하고 각 작은 부분을 특화 에이전트에게 할당, 전체 에이전트 워크플로우가 문제없이 흐를 수 있는 시스템을 갖춘다.
>
> 그리고 앞으로 만들어야 하는 도구는 사람이 사용하기 위한 도구가 아니라 에이전트가 사용할 수 있는 도구를 만들어야 한다.

> 에이전트를 에이전트답게 사용하는 것은 에이전틱하게 사용하는 것. 의미는, 에이전트가 하는 일을 일일이 감시하는 게 아니라, 목표와 통과 기준을 주고 일 자체에서 빠지는 것.

## 에이전틱하게 쓴다는 것

에이전트를 쓰면서도 사람이 모든 단계를 지켜보고 승인하고 있다면, 그건 자동화된 도구를 손으로 돌리는 것에 가깝다. 에이전트답게 쓴다는 건 다르다.

- 사람이 주는 것은 **목표**와 **통과 기준**이다. "무엇이 되면 끝인가"를 분명히 한다.
- 그다음 사람은 **일에서 빠진다.** 중간 과정을 일일이 확인하거나 단계마다 승인하지 않는다.
- 에이전트는 기준을 스스로 확인하며 끝까지 간다. 막히면 스스로 풀고, 정말 사람만 정할 수 있는 결정만 올린다.
- 그래서 통과 기준을 잘 쓰는 것이 일의 대부분이 된다. 기준이 흐릿하면 사람이 다시 들어가 감시하게 된다.

이번 출시에서 내가 계속 확인 요청을 받은 건, 이 구조가 아니었기 때문이다. 목표("출시")와 기준("dev DB에서 실제로 동작하면 배포 끝까지")을 준 뒤에야 팀이 스스로 굴러가기 시작했다.

## 배경: 출시 하나를 봇 팀으로 끝까지 밀어 보며

디스코드에 띄운 Claude·Codex 봇 20여 개로 교회 앱 '스르스르'의 가입 승인 기능을 출시했다. 개발·리뷰·보안·QA는 일찍 끝났는데, 실제 배포까지 하루가 걸렸다. 막힌 곳은 코드가 아니라 흐름이었다.

- 리드 봇이 하위 작업이 끝나도 다음 일을 맡기지 않고 멈췄다(5번 넘게).
- 작업이 리드 → 하위 → 하위로 넘어가며 알림이 끊겼다.
- 매번 출시마다 절차가 달라졌다. 있는 출시 스킬을 안 쓰고 사람에게 콘솔 확인을 부탁하기도 했다.
- 안전장치가 개발을 막았다. 오류 로그를 가리고, 진단 하나에 봇 셋이 차례로 넘겼다.
- 도구가 사람용이었다. DB·클라우드 콘솔, 승인 형식, 스토어 콘솔이 사람 손을 요구해서 그때마다 내가 들어가야 했다.

## 원칙 1. 큰 흐름은 워크플로우로, 작은 부분은 특화 에이전트에게

- 출시·QA·배포 같은 반복되는 큰 흐름을 단계와 넘김 조건이 있는 워크플로우로 고정한다. 에이전트가 매번 절차를 새로 발명하지 않게.
- 각 단계는 그 일만 하는 특화 에이전트가 맡는다. 단계의 입력·출력·합격 기준이 분명하면 같은 수준으로 반복된다.
- 흐름 자체를 지켜보는 장치가 필요하다. 멈춤·누락·끊긴 알림을 감지하고 다시 밀어 주는 역할. (지금은 비서 봇이 1분마다 작업판을 감시하고 독촉한다.)
- 사람은 정말 사람만 정할 수 있는 결정에만 들어온다.

## 원칙 2. 도구는 에이전트가 쓸 수 있게

- 사람용 콘솔(클릭, 화면 확인)을 기준으로 만들면 에이전트가 쓸 때마다 사람이 끼어야 한다.
- 에이전트용 도구의 조건(초안):
  - 명령 하나로 실행되고, 결과가 기계가 읽을 수 있는 형태로 나온다.
  - 권한이 좁고 명확하다(그 앱·그 브랜치만).
  - 비밀값은 도구 안에서만 쓰고 대화·로그에 남지 않는다.
  - 실패 이유가 원문 그대로 보인다(가리지 않는다).
  - 승인이 필요하면 에이전트가 검증 가능한 형식으로 받는다.
- 예: 웹 배포 확인을 사람이 AWS 콘솔에서 보던 것을, 범위를 좁힌 키로 에이전트가 직접 조회하게 바꿨다.

## 나중에 구체화할 것

- 워크플로우를 무엇으로 표현할지(문서/스킬, 상태 기계, 실제 오케스트레이터).
- 단계 간 넘김 계약: 입력·출력·합격 기준·되돌리기.
- 흐름 감시자 설계: 무엇을 멈춤으로 볼지, 언제 사람에게 올릴지.
- 에이전트용 도구 설계 체크리스트와 사례 모음.
- 안전장치와 자율성의 균형: 어디까지 에이전트가 스스로 판단하게 할지.
