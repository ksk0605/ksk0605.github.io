Lauren Tan의 pstack은 에이전트에 작업 절차를 주고, 실제 앱의 동작과 중요한 상태 규칙을 반복 검증할 방법을 프로젝트에 남기는 MIT 라이선스 스킬 모음이다.

- Lauren Tan의 Cursor 플러그인이 원본이다. `backnotprop/pstack`은 Claude Code·Codex·Pi 등에서 스킬을 따로 쓸 수 있게 만든 미러다.
- `create-verification-skill`은 실행·조작·증거 수집법을 만들고, `maintain-verification-skill`은 앱이 바뀐 뒤에도 그 방법이 유효한지 확인한다.
- `statechart`는 모델을 검사하고, 규칙이 깨지는 경우 그 상태에 도달하는 경로를 보여 준다. 실제 앱의 동작은 별도로 검증해야 한다.

## 무엇을 풀려는 도구인가

에이전트가 코드를 고치고 단위 테스트를 통과해도, 사용자 화면에서는 처음 문제를 보고한 동작이 여전히 실패할 수 있다. 다음 에이전트가 앱을 띄우는 방법부터 다시 찾거나, 재현하기 쉬운 경로만 확인하면 이 공백이 반복된다. pstack은 실제 사용 경로를 실행 가능한 절차로 기록한다. 검증한 기능이 어디에 있고, 어떤 조작을 해야 하며, 무엇이 보이면 성공인지 기능 지도에 남긴다.

발표 [「All Code Is Slop (Except Mine)」](https://ai.engineer/talks/O_zcc6Xl12g-all-code-is-slop-except-mine)에서 Lauren Tan은 코드베이스와 정적 검사, 실제 동작 검증, 형식 검증에 각기 다른 역할을 둔다. [한국어 발표 해설](https://ksk0605.github.io/posts/all-code-is-slop-except-mine/)에서 말한 기능 지도와 상태도는, 저장소에서는 아래의 검증 스킬과 `statechart`로 이어진다. 발표에서 언급한 팀 전체 도구를 이 플러그인 하나가 제공하는 것은 아니다. [Cursor 원본](https://github.com/cursor/plugins/tree/main/pstack) · [미러 README](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/README.md)

## 핵심 워크플로 네 가지

### 1. `poteto-mode`가 작업 유형에 맞는 절차를 고른다

[`skills/poteto-mode/playbooks/bug-fix.md` 10행](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/poteto-mode/playbooks/bug-fix.md#L10) 발췌.

```text
Verify on the same surface. The original repro now passes.
```

버그 수정 플레이북은 먼저 원래 동작을 재현하고, 실행 증거로 원인을 좁히고, 고친 뒤 같은 화면이나 인터페이스를 다시 검증하라고 한다. Android 앱에서 화면이 깨진 문제를 웹에서만 확인했다면 Android 결과는 미확인이다. 호스트별로 서브에이전트, 모델 설정, 실제 앱 조작 도구가 달라진다. 모드 전체를 쓰기 전 사용할 플레이북의 전제 도구를 확인할 필요가 있다. [모드와 호스트별 매핑](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/poteto-mode/SKILL.md#L102-L120)

### 2. `create-verification-skill`은 검증 방법을 다음 작업에 남긴다

[`skills/create-verification-skill/SKILL.md` 28행](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/create-verification-skill/SKILL.md#L28) 발췌.

```text
one read-only check that answers "is this instance worth driving?"
```

저장소에서 실행법과 로그인·데이터 조건, 기존 테스트 도구, 격리 가능성을 먼저 조사한다. 그 결과로 `Launch / Doctor / Drive / Evidence / Cleanup`이 들어 있는 `verify-<app>/SKILL.md`와 기능 지도를 만든다. `Doctor`는 버전, 포트, 인증 상태를 점검한다. `Evidence`는 최종 화면과 함께 사용자가 한 행동, 그 결과, 필요한 부작용까지 기록한다. 생성한 스킬은 적어도 한 기능을 시작부터 정리까지 실행해 증거가 남는지 확인해야 초안을 벗어난다. [생성 스킬](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/create-verification-skill/SKILL.md#L23-L40)

### 3. `maintain-verification-skill`은 앱이 바뀌어도 기능 지도를 검증한다

[`skills/maintain-verification-skill/SKILL.md` 33행](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/maintain-verification-skill/SKILL.md#L33) 발췌.

```text
**Live pass.** Required even when source looks clean.
```

소스에서 화면 경로·조건이 바뀌었는지 읽은 뒤, 코디네이터가 기능 지도의 각 경로를 실제로 조작한다. 실제 앱 결함과 낡은 테스트 절차를 분리하고, 인증이나 환경 조건 때문에 접근할 수 없으면 무엇이 부족했는지 기록한다. 검증 도구를 고쳤다면 다시 실행한다. 정리 후에도 증거는 남긴다. [유지 스킬](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/maintain-verification-skill/SKILL.md)

### 4. 형식 검증과 `statechart`는 틀릴 수 있는 순서를 보여 준다

[`skills/statechart/SKILL.md` 16행](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/statechart/SKILL.md#L13-L21) 발췌.

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

예를 들어 “승인이 취소된 뒤 이전 요청의 재시도가 성공할 수 있는가?”처럼 사건 순서가 핵심이면 TLA+로 작은 모델과 검사할 규칙을 쓸 수 있다. `statechart`는 TLC 결과를 바탕으로 Mermaid 상태도와, 규칙 위반에 도달하는 경로를 만든다. 코드 자체의 메모리 안전성이나 모든 입력에서의 성질을 묻는다면 형식 검증 생성 스킬은 실제 코드에 맞는 다른 검증 도구를 고르라고 한다. 모델 검사 결과에는 모델의 범위, 가정과 검사되지 않은 규칙을 함께 적어야 한다. [형식 검증 생성 스킬](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/create-formal-verification-skill/SKILL.md) · [상태도 보고서 해석](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/skills/statechart/SKILL.md#L62-L76)

## 설치와 사용법

미러 README는 Node.js의 `npx`로 `skills` CLI를 실행하는 설치법을 안내한다. 목록에서 필요한 스킬과 대상 에이전트를 선택한다.

```sh
npx skills add backnotprop/pstack
```

실제 앱 검증부터 시작한다면 `create-verification-skill`과 `maintain-verification-skill`을 함께 고른다. 형식 검증용 생성·유지 스킬에는 `statechart`도 함께 설치한다. Cursor 원본은 `/add-plugin pstack`, Claude Code용 공식 어댑터는 `pstack@cursor-plugins`를 안내한다. 미러 방식은 개별 스킬만 골라 넣을 수 있어 여러 에이전트를 섞어 쓰기에 편하다. `statechart` 문서상 첫 실행은 mise로 Java와 TLC를 준비하므로 네트워크와 TypeScript 실행 환경이 필요하다. 이 글의 설치·사용법은 문서에서 확인한 내용이다. [미러 설치](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/README.md#install) · [Claude Code 어댑터](https://github.com/backnotprop/pstack/blob/83a729a182a29b59a2a42fc3d7736b0c376b55d4/docs/harness/claude-code.md)

## 장점과 한계

가장 큰 장점은 같은 경로를 다시 테스트하기 쉬워진다는 점이다. 앱을 켜서 눈으로 확인했다는 한 줄 대신, 어떤 빌드와 환경에서 무엇을 눌렀고 어떤 증거가 남았는지 다음 QA가 재현할 수 있다. 팀은 앱 검증용 두 스킬만 가져와도 이 방식을 쓸 수 있다.

그만큼 기능 지도와 실행 절차를 유지할 일이 생긴다. 도구·모델·서브에이전트 지원이 달라 동일한 프롬프트가 모든 호스트에서 같은 경로를 타지는 않는다. 에뮬레이터와 테스트 서버에서 확인한 범위는 실기기, 운영 백엔드, 외부 인증까지 자동으로 넓어지지 않는다. 형식 검증도 모델에 적힌 가정과 범위까지만 증거가 된다. 성과를 비교할 때 에이전트 호출 수보다 재현 가능 여부와 아직 검사하지 않은 범위를 먼저 보는 편이 낫다.
