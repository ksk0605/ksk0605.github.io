Garry Tan의 gstack은 제품 기획, 설계 검토, QA, 릴리스 작업을 Claude Code 중심의 스킬과 실행 도구로 묶은 MIT 라이선스 프로젝트다.

- `/office-hours`에서 만든 설계 문서와 검토 메모가 다음 단계의 입력으로 이어진다.
- `/qa-only`는 재현 증거를 남기고, `/qa`는 수정과 재검증까지 할 수 있다.
- `/ship`은 테스트·리뷰·최종 변경분 검증을 거쳐 PR을 올린다. Claude Code와 Codex에서 제공하는 기능 범위는 다르다.

## 무엇을 풀려는 도구인가

하나의 대화에서 “이 기능을 만들어 줘”라고 하면, 문제 정의부터 배포 준비까지 모델이 알아서 순서를 정한다. 실행은 빠르지만 기획 때 합의한 제약이 QA 단계까지 전달됐는지, 실제로 검토한 코드가 PR에 들어갔는지 확인하기 어렵다. gstack은 이 연결을 설계 문서, 테스트 계획, 재현 보고서와 검증 기록으로 남긴다. 모든 명령을 차례대로 실행할 필요는 없다. 아이디어 구체화만 필요하면 `/office-hours`, 이미 열린 PR의 재현이 필요하면 `/qa-only`를 쓸 수 있다. [README](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/README.md)

## 저장소 구조

| 경로 | 무엇이 들어 있나 |
| --- | --- |
| `office-hours/`, `autoplan/`, `plan-*-review/` | 제품 문제 정의 및 CEO·디자인·개발자 경험(DX)·엔지니어링 관점의 계획 검토 |
| `review/`, `qa/`, `qa-only/`, `verify/` | 변경분 검토, 실제 동작 재현과 수정, 보고 전용 QA, 저장소 자체 검사 |
| `ship/`, `land-and-deploy/`, `document-release/` | PR 작성과 검증, 별도 병합·배포 흐름, 릴리스 문서 |
| `browse/`, `bin/`, `setup` | 브라우저 구동 코드, 보조 명령, 빌드와 호스트별 스킬 등록 |
| `docs/`, `hosts/`, `crew/` | 설치·운영 문서, 호스트 지원 설정, Capy 전용 다중 에이전트·머지 큐 도구 |

스킬 폴더에는 생성에 쓰는 `SKILL.md.tmpl` 파일이 있다. 브라우저 QA는 macOS에서 Aside가 켜져 있으면 그 브라우저를 우선 사용한다. 사용할 수 없으면 지속 실행되는 Chromium을 로컬 CLI로 제어한다. 같은 브라우저의 탭·쿠키 상태를 여러 작업 사이에 유지할 수 있다. [저장소 트리](https://github.com/garrytan/gstack/tree/44170d67916dc80a008803f7b3f7cbf7dbe32ea7) · [아키텍처](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/ARCHITECTURE.md)

## 핵심 워크플로 네 가지

### 1. `/office-hours`로 구현 전에 문제를 좁힌다

[`office-hours/SKILL.md.tmpl` 68행](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/office-hours/SKILL.md.tmpl#L66-L68) 발췌.

```text
Your only output is a design document.
```

Startup 모드에서는 문제의 필요성과 전제를 질문하고, Builder 모드에서는 만들고 싶은 것의 범위와 선택지를 구체화한다. 예를 들어 “온보딩을 바꿔 달라”는 요청은 어느 단계에서 누가 막히는지, 기존 사용자에게 무엇을 보존할지부터 정리하는 설계 문서가 된다. 이 문서가 다음 계획 검토에 들어간다.

### 2. `/autoplan`은 엔지니어링 검토를 마지막에 둔다

[`autoplan/SKILL.md.tmpl` 98~99행](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/autoplan/SKILL.md.tmpl#L98-L99) 발췌.

```text
Phases MUST run in strict order: CEO → Design (if UI scope) → DX (if developer-facing
scope) → Eng. Eng runs LAST, always, reviewing all prior amendments.
```

기획 관점을 먼저 보고 UI나 개발자 대상 변경이 있을 때 해당 검토를 추가한다. 마지막 엔지니어링 검토는 그간의 수정을 모두 반영한 계획을 대상으로 한다. 대화형 명령과 무인 `gstack-autoplan`의 검토 깊이는 다르다. README에 따르면 무인 기본 실행은 짧은 체크리스트의 검토자 한 명을 쓰고, `--full`은 단계마다 검토자를 둔다. [실행별 검토 범위](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/docs/skills.md#what-each-run-loads)

### 3. `/qa-only`는 재현을 맡기고 수정은 별도로 넘긴다

[`qa-only/SKILL.md.tmpl` 29~31행](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/qa-only/SKILL.md.tmpl#L27-L31) 발췌.

```text
Explore the selected surfaces and report reproducible behavior with evidence.
**NEVER fix anything or change product tests.**
```

브라우저뿐 아니라 API, CLI, 작업 큐, 웹훅도 대상으로 삼을 수 있다. 독립 QA가 재현 위치, 입력, 기대 결과, 실제 결과와 캡처를 남기고, 구현 담당에게 수정 작업을 넘기는 데 쓸 수 있다. 한 세션에서 수정과 재검증을 맡기려면 `/qa`가 그 흐름을 제공한다. [수정형 QA 스킬](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/qa/SKILL.md.tmpl) · [브라우저 밖의 QA](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/docs/qa-without-a-webpage.md)

### 4. `/ship`은 올릴 변경분과 검토 증거를 연결한다

[`ship/SKILL.md.tmpl` 44~45행](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/ship/SKILL.md.tmpl#L44-L47) 발췌.

```text
**Route:** integrate (1–3) → test and review (4–11.5) → prepare the release
(12–15) → verify frozen content (16) → push and publish (17–21).
```

대상 브랜치를 통합한 뒤 테스트와 리뷰를 하고, 필요한 버전·변경 기록·문서를 준비한다. 그 뒤 검토한 결과가 실제 올릴 내용과 맞는지 다시 검사한다. 이전 검증을 재사용할 때도 조건과 기록을 확인한다. 이 흐름은 원격 push와 PR 작성까지 이어질 수 있다. 실제 병합·배포는 저장소의 별도 명령인 `/land-and-deploy`에서 다룬다. [검증 단계](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/ship/SKILL.md.tmpl#L374) · [병합·배포 스킬](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/land-and-deploy/SKILL.md.tmpl)

## 설치와 사용법

README 기준으로 Git과 Bun이 필요하다. 문서는 Bun 1.4.2 이상을 테스트 버전으로 들며 1.3.3 미만의 설치를 거절한다고 설명한다. Windows에는 Node.js가 추가로 필요하다. 아래는 공식 README에 나온 두 호스트의 설치 방식이다. 실습에는 같은 프로젝트에서 두 명령을 연달아 돌릴 필요 없이 사용하는 호스트를 고르면 된다.

```sh
git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack
cd ~/.claude/skills/gstack
./setup               # Claude Code
./setup --host codex  # Codex를 쓸 경우 이 명령 선택
```

Claude Code에서는 `/office-hours`나 `/qa-only`를 호출한다. Codex에서는 `gstack-office-hours`처럼 이름으로 지정할 수 있다. Codex는 실험 지원으로 분류되고, Claude Code에서 훅으로 차단하는 일부 절차가 Codex에서는 권고로만 작동한다. Claude Code 설치는 훅을 등록하며, 팀 모드는 세션 시작 자동 업데이트를 사용한다. 이 글은 파일과 문서에 근거하며 설치 상태나 실행 결과는 확인하지 않았다. [설치 문서](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/docs/install.md) · [호스트별 지원](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/docs/hosts.md)

## 장점과 한계

장점은 단계마다 누가 무엇을 확인했는지 기록이 남는다는 점이다. 특히 보고 전용 QA와 수정형 QA를 구분하고, 리뷰한 변경분을 실제 릴리스 후보와 맞춰 보는 설계는 사람이 나중에 결과를 검토하기 쉽게 한다. 이미 GitHub와 CI에서 일하는 팀은 필요한 단계만 가져와 적용할 수 있다.

큰 변경에 쓰는 검토 체인을 간단한 수정마다 돌리면 대기 시간과 모델 사용량이 늘어난다. 훅의 강제력은 호스트마다 다르고, 브라우저가 로그인된 Aside를 사용하면 검증 중에도 실제 계정 세션을 만질 수 있다. README는 사용량 텔레메트리 기본값이 꺼져 있다고 설명하지만, 업데이트 확인과 외부 모델 리뷰는 기본으로 켜져 있다. 외부 리뷰를 쓰면 로그인한 Codex 또는 Claude Code로 코드가 전송된다. Capy 전용 머지 큐와 실행 기록도 일반 Mac 설치에서 자동으로 제공되는 범위에 포함되지 않는다. [개인정보·외부 전송](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/docs/privacy.md) · [Capy 도구](https://github.com/garrytan/gstack/blob/44170d67916dc80a008803f7b3f7cbf7dbe32ea7/crew/README.md)
